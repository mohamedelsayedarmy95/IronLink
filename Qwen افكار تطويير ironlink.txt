## ⚖️ STRATEGIC TRADE-OFF FRAMEWORK

When making product or engineering decisions, apply the following hierarchy:

1. **Privacy and security must not be silently weakened.**
2. **E2EE features cannot be combined with server-side AI/read access unless an explicit opt-in non-E2EE mode is used.**
3. **AI features must be designed as privacy-aware modes:**
   - Secret E2EE mode: local-only intelligence where possible
   - Cloud mode: server-assisted intelligence with explicit consent
   - Company mode: policy-controlled intelligence and auditability
4. **Zero-cost ambition must not compromise reliability, security, or legal compliance.**
5. **Feature richness must not destroy speed, stability, or usability.**
6. **Company Mode must not be built before core messaging is stable unless explicitly requested.**
7. **Monetization must never compromise user trust.**
8. **Admin visibility in Company Mode must never leak into normal user-facing social experiences.**
9. **Contact discovery must never expose raw phone numbers, contact books, or social graphs beyond the user's consent.**
10. **Network growth features must preserve privacy-first principles and must not turn IronLink into a contact-scraping platform.**
11. **Multilingual support must never compromise the user experience in any language; all languages are first-class citizens.**
12. **Translation features must preserve meaning, cultural nuance, and user intent without bias.**
13. **Content moderation must be culturally aware and language-sensitive.**

### 🌐 User Language Flow

1. **First Launch**:
   - App detects device language
   - If supported, app loads in that language
   - If not, app asks user to select a language

2. **User Settings**:
   - Users can change language at any time
   - Users can enable/disable auto-translation
   - Users can select primary and secondary languages

3. **Chat Experience**:
   - Messages appear in the user's preferred language
   - If message is in a different language, user can translate with one tap
   - Users can enable auto-translation for all incoming messages

4. **Voice Messages**:
   - Voice notes are transcribed in the user's language
   - Users can translate voice transcriptions
   - Future: real-time voice translation

5. **Community Participation**:
   - Posts appear in the user's preferred language
   - Users can contribute translations for community content
   - Moderators can approve/reject community translations

#### Translation Engine (Free/Open-Source)

- **Primary**: Hugging Face free inference API (Helsinki-NLP/opus-mt-* models)
- **Backup**: Local open-source models (if self-hosted)
- **Cache**: Redis cache for translations (TTL: 30 days)
- **Rate Limiting**: Prevent abuse of translation API

#### Language Detection

- **Primary**: Hugging Face free inference API (fasttext language detection)
- **Backup**: Google Translate API (if needed, but avoid)
- **Cache**: Redis cache for language detection

#### Localization (i18n/l10n)

- **Flutter**: `flutter_localizations` + `intl` packages

## 🔢 INTERNAL EMPLOYEE IDENTIFICATION (ADMIN-ONLY MAPPING)

Enhance Company Mode by adding an **internal identification system** that allows organizations to map each user to an internal reference number used only for administrative, organizational, auditing, or workforce-management purposes.

This identifier is **not** the user's public identity. The user still registers with their normal name and appears to other users normally. The internal ID exists only as an admin-facing mapping layer inside the company space.

### Core Concept

In Company Mode, each member may be associated with an optional or required internal identifier, depending on the company's configuration.

The internal identifier helps the Super Admin, admins, and authorized HR/security officers identify employees, staff members, military personnel, or organization members without affecting the normal social/user experience inside the app.

- Regular users must **not** see other members' internal IDs.
- The internal ID must **not** appear in public profiles, normal chat headers, community member lists, or user search results for non-admin users.

  - Admin lookup

  - Attendance or operational tracking

## 📇 CONTACTS SYNC & AUTO-DISCOVERY ENGINE (Full Specification — Better than WhatsApp)

## 🎯 Purpose

Build a world-class contact synchronization and auto-discovery system so that **any user who installs IronLink is instantly discoverable by their existing contacts, and can immediately discover and chat with contacts who already use the app** — with zero friction, total privacy, and a smoother experience than WhatsApp.

## 🧠 Core Principles

1. **Zero-friction discovery**: A new user should appear to their contacts automatically, and see their contacts automatically, without manual searching.
2. **Privacy-first matching**: Raw phone numbers are never uploaded or stored. Only salted cryptographic hashes or privacy-safe tokens are matched.
3. **Mutual consent**: Discovery respects each user's "Who can find me" privacy setting.
4. **Instant gratification**: The moment a contact joins, both sides can start chatting in under 2 taps.
5. **Reversible & deletable**: Users can opt out and have all synced contact data permanently erased.
6. **No social graph leakage**: The system must not expose non-IronLink contacts, non-matching hashes, or the full contact book to anyone.
7. **Contactless fallback**: Users who refuse contacts permission can still connect via username, QR code, invite link, or share profile.

## 🔄 End-to-End Sync Flow

### Step 1 — Permission & Capture

- On first launch (or on-demand), request the OS contacts permission with a clear value-explanation screen.
- Read the device contact book locally on the device.
- If permission is denied, offer username/QR/invite alternatives without blocking app usage.

### Step 2 — Privacy-Preserving Hashing (On-Device)

- Normalize each phone number to E.164 format.
- Hash each number with SHA-256 plus a server-provided random salt, or use a Private Set Intersection scheme for stronger privacy.
- Only the hashes/tokens leave the device. Raw numbers never touch the server.
- Store only the minimum required data for matching.

### Step 3 — Server-Side Matching

- The backend compares submitted hashes against a hashed index of all registered users' phone numbers who allow discovery.
- Return only the matches that correspond to real IronLink users AND who allow discovery.
- Do not reveal which non-matching hashes were submitted.
- Do not expose users who disabled discovery.

### Step 4 — Auto-Display & Linking

- Discovered contacts are shown in a dedicated **"Contacts on IronLink"** tab.
- Each discovered contact is linked to their IronLink profile (avatar, username, presence).
- The user can tap once to **open a chat** immediately.
- If the contact has no existing chat, create or suggest a new chat with one tap.

### Step 5 — Real-Time Join Notifications

- When a contact later registers on IronLink, the system pushes a notification: **"🎉 [Name] joined IronLink — Say hi!"** with a direct "Open Chat" action.
- The new user's device also runs discovery and sees existing contacts instantly.
- Join notifications respect privacy settings and do not notify if discovery is disabled.

### Step 6 — Invite the Rest

- Contacts not yet on IronLink are shown under **"Invite"**, with one-tap SMS/share invite containing a deep-link to install and auto-connect.
- Invite links may carry an inviter reference for attribution but must not expose the invitee's phone number.
- Invites must be rate-limited to prevent spam.

## 🏗️ Technical Architecture for Contacts Sync

### Backend Additions

- `app/models/contact_hash.py` — store per-user hashed contacts (hash, owner_id, created_at)
- `app/models/user_phone_index.py` — hashed phone index of registered users for matching
- `app/models/contact_relation.py` — resolved links between a user and discovered IronLink contacts
- `app/models/contact_invite.py` — invite tracking, tokens, attribution, and install conversion
- `app/api/routes/contacts.py` — endpoints: `/contacts/sync`, `/contacts/matches`, `/contacts/invite`, `/contacts/delete-all`
- `app/services/contact_discovery_service.py` — hashing, matching, private-set-intersection logic
- `app/services/contact_sync_worker.py` — background batch matching + join-event detection
- `app/services/invite_service.py` — generate deep-link invites, track installs, prevent abuse

### Matching Algorithm

- Use Private Set Intersection (PSI) or batched hash lookups to match contacts without exposing non-matches.
- Cache the hashed phone index in Redis for sub-second matching.
- Trigger an async re-match whenever a new user registers, to notify existing users who have that number.
- Use pagination and chunked uploads for large contact books.
- Apply exponential backoff and retry for failed sync jobs.

### Database Tables for Contacts Sync

- `contact_hashes` (id, user_id, phone_hash, created_at) — indexed on phone_hash
- `user_phone_index` (user_id, phone_hash, allows_discovery, updated_at)
- `contact_relations` (id, user_id, contact_user_id, source, linked_at)
- `contact_invites` (id, inviter_id, phone_hash, invite_token, installed_at)
- `contact_sync_jobs` (id, user_id, status, total_contacts, matched_count, created_at, completed_at)
- `contact_sync_settings` (user_id, sync_enabled, discovery_by_phone_allowed, last_sync_at)

### Flutter Additions for Contacts Sync

- `lib/features/contacts/` — full feature module
- `screens/contacts_permission_screen.dart` — value-explanation + permission request
- `screens/contacts_discovery_screen.dart` — "On IronLink" / "Invite" tabs
- `bloc/contacts_bloc.dart` — sync state management
- `services/contact_sync_service.dart` — local read, hashing, incremental diff
- `widgets/contact_card.dart` — avatar, name, presence, "Open Chat" button
- `widgets/invite_sheet.dart` — share/SMS invite bottom sheet
- `widgets/contacts_consent_sheet.dart` — privacy explanation and opt-in/opt-out controls

### Privacy Controls for Contacts Sync

- **Sync toggle**: Enable/disable contact sync.
- **Who can find me by phone**: Everyone / Contacts of Contacts / Nobody.
- **Delete synced data**: Permanently erase all uploaded hashes and relations.
- **Show me to new contacts**: Whether I appear when a new contact joins.
